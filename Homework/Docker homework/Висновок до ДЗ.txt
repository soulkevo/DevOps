1.Ефект кешу Docker
    Під час першої збірки Docker виконав усі необхідні шари образу. Після зміни лише одного символу в app.py та повторної збірки Docker використав кеш для незмінених шарів, зокрема для встановлення залежностей.
    Тому друга збірка виконувалась швидше. Це показує, що правильний порядок інструкцій у Dockerfile дозволяє ефективніше використовувати Docker cache.

2.Зв'язок двох сервісів через Compose
    За допомогою Docker Compose було запущено два сервіси: app та db. Застосунок звертається до бази даних за ім'ям сервісу db, а не через localhost. Для PostgreSQL налаштовано healthcheck, який перевіряє готовність бази до прийому підключень.
    Застосунок запускається після того, як база переходить у стан healthy. Для збереження даних PostgreSQL використовується Docker volume.

3.Зламати та полагодити healthcheck
    Для перевірки роботи healthcheck його було навмисно змінено на некоректний. У результаті контейнер PostgreSQL перейшов у стан unhealthy, а застосунок не зміг запуститися через залежність service_healthy.
    У консолі з'явилося повідомлення:
        dependency failed to start: container task91-db is unhealthy
    Після відновлення правильного healthcheck база знову перейшла у стан healthy, а застосунок успішно запустився.

4.Публікація порту бази
    Для перевірки було тимчасово опубліковано порт PostgreSQL через ports:
    5432:5432
    У результаті Docker показав проброс 0.0.0.0:5432->5432/tcp.
    Публікувати порт бази даних назовні без необхідності не варто. Для взаємодії між контейнерами достатньо внутрішньої Docker-мережі, де застосунок може звертатися до PostgreSQL за адресою db:5432.
    Відсутність публічного порту зменшує поверхню доступу до бази даних.
    Після перевірки ports для PostgreSQL було прибрано.
